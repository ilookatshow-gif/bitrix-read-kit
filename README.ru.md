# Проверяем, есть ли незавершённое дело у каждой сделки в Битрикс24

**Bitrix read kit** отвечает на простой рабочий вопрос: у каких доступных вам
сделок в работе не найдено незавершённого CRM-дела? Отдельно показывает дела со
сроком, просроченные и без срока. Вместо оценки менеджера — конкретные ID и
понятная граница полноты данных.

[English guide](README.md) ·
[Общий каталог Lookatshow](https://github.com/ilookatshow-gif/lookatshow-open-tools)

[Скачать ZIP v0.1.0](https://github.com/ilookatshow-gif/bitrix-read-kit/releases/download/v0.1.0/bitrix-read-kit-0.1.0.zip) · [Проверки установки](https://github.com/ilookatshow-gif/bitrix-read-kit/actions/workflows/ci.yml)

Бесплатный модуль работает отдельно от платного ядра. Учебный пример не требует
аккаунта Битрикс24, интернета или установки библиотек. Это Python CLI, не
MCP-сервер. Выпуск кода и учебные проверки не подтверждают доступ к вашему
настоящему порталу: его разрешения и REST-ответы проверяются отдельно.

## Что вы получите

Минимальный снимок доступных сделок в работе и воспроизводимый локальный отчёт.
Для каждой сделки сохраняется отдельный признак полноты чтения дел. Если выборка
завершена и пуста, можно сказать `no_visible_open_activity` — в доступной выборке
не найдено незавершённого CRM-дела. Если чтение оборвано, такой вывод делать нельзя.
Просроченное дело существует; его нельзя записывать в отсутствующие. Срок
`9999-12-31` — специальный признак «срок не установлен», а не встреча в далёком
будущем.

Это не поиск «потерянных продаж», не полный аудит портала и не оценка сотрудников.
Договорённость с клиентом может быть в переписке, звонке, задаче или другой
системе. Даже незавершённое входящее письмо само по себе не доказывает, что с
клиентом согласован следующий шаг. API отдаёт только записи, доступные пользователю
webhook: успешный ответ не означает доступ ко всей CRM компании.

### Сначала посмотрите на результат, ничего не подключая

В комплекте **вымышленный учебный снимок** из пяти сделок. На
`2026-10-10T10:00:00+03:00` ожидаемый локальный пример такой:

| Учебная сделка | Что видно в данных | Какой вывод допустим |
| --- | --- | --- |
| `101` | Дела прочитаны полностью, незавершённых нет | В доступной выборке нет незавершённого CRM-дела. |
| `102` | Незавершённое дело `201`, срок 10 октября, 12:00 МСК | Есть запланированное дело. |
| `103` | Незавершённое дело `202`, срок 9 октября | Есть просроченное дело. |
| `104` | Незавершённое дело `203`, специальный признак «без срока» | Есть дело без срока; завершённое `204` не считается незавершённым. |
| `105` | Чтение дел неполное | Нельзя утверждать, что дел нет. |

Уникальных видимых незавершённых дел — три. Счётчики признаков
**не взаимоисключающие**: у настоящей сделки могут одновременно быть
просроченное и запланированное дела. Это учебные данные, не результаты клиента.

## Установка без лишних зависимостей

Нужен Python **3.9+**, только стандартная библиотека. В распакованной папке:

```bash
python3 install.py --prefix "$HOME/.local/lookatshow-bitrix-read"
"$HOME/.local/lookatshow-bitrix-read/bin/lookatshow-bitrix-read" doctor
"$HOME/.local/lookatshow-bitrix-read/bin/lookatshow-bitrix-read" demo
```

Папка prefix должна быть новой; её родительская папка — уже существовать.
Если установка у вас уже есть, выберите другое имя. Установщик отказывается
работать через символические ссылки или внутри исходной папки, проверяет точный
список `MODULE.json` и не копирует произвольное содержимое. Команда оказывается
в `bin/`, пакет — в `lib/bitrix-read-kit/`. Импорты работают и при запуске из
другой рабочей папки. PATH, профиль терминала и системные настройки не меняются.

Короткое имя можно включить только для текущего сеанса POSIX-терминала:

```bash
export PATH="$HOME/.local/lookatshow-bitrix-read/bin:$PATH"
lookatshow-bitrix-read --help
```

На Windows используйте `python`, если так называется ваш интерпретатор;
установленная команда — `bin\lookatshow-bitrix-read.cmd`. Приложенный skill
остаётся внутри модуля: установщик не регистрирует его глобально в Codex или Claude.

### Проверка локального пакета

```bash
python3 -B -m unittest discover -s tests -v
python3 -B tests/smoke_install.py
```

Smoke-проверка устанавливает ровно 15 файлов из whitelist в новую папку с пробелами
и кириллицей, запускает штатную команду из другой папки и повторяет установленные
тесты. На Windows выбирается настоящий `.cmd`, на POSIX — исполняемый wrapper.
Локальная проверка выполнена на macOS arm64/Python 3.9.6. В комплекте есть CI для
Ubuntu 24.04/Python 3.9 и 3.12, Windows Server 2022/Python 3.12 и macOS 15/Python 3.12.
Проверяйте результат конкретного запуска на [странице Actions](https://github.com/ilookatshow-gif/bitrix-read-kit/actions/workflows/ci.yml):
наличие workflow не равно прошедшему запуску. Отдельные subprocess-тесты используют вывод `cp1252`
и проверяют русское приветствие один раз, валидный снимок по кириллическому пути
и квитанцию установки в кириллический prefix. Подставная кодировка вывода сама
по себе не подтверждает работу на Windows.

Для удаления перестаньте использовать команду и удалите через файловый менеджер
только выбранную папку prefix. Если нужны реальные снимки CRM, храните их
отдельно. Не удаляйте родительскую `.local`, домашнюю или рабочую папку.

## Шесть понятных команд

| Команда | Что делает |
| --- | --- |
| `doctor` | Офлайн проверяет конфигурацию и наличие авторизации. Не показывает webhook и не обращается к порталу. |
| `demo` | Анализирует вымышленные учебные данные. Без сети и авторизации. |
| `validate --input PATH` | Проверяет контракт локального JSON-снимка. |
| `audit --input PATH --as-of RFC3339` | Строит локальный отчёт на явно указанное время с часовым поясом. |
| `capture --out NEW_PATH --max-deal-pages 2 --max-activity-pages 2` | По прямому запросу ограниченно читает CRM через HTTPS и создаёт новый локальный файл. Нужна `B24_WEBHOOK_URL`. |
| `onboard --state-dir PATH` | По желанию показывает приветствие автора один раз для выбранной папки состояния. |

По умолчанию команды выводят JSON; флаг `--json` не нужен. Справка `--help`
обычная текстовая. Нет произвольного `request`, скрытой записи в CRM или фонового
планировщика. Ошибка даёт ненулевой exit status и безопасный код: сырой ответ
провайдера и секретный URL не выводятся в консоль. Формат ошибки —
`{"ok": false, "error": {"code": "...", "message": "..."}}`.
Успешно сформированный отчёт
может честно сообщать о неполноте — проверяйте признаки полноты, а не только
код завершения процесса.

JSON в консоли использует ASCII-экранирование Unicode: это сохраняет русские
строки при старых кодировках вывода и не выдаёт ошибку установки после успешного
копирования файлов. JSON-парсер восстанавливает исходный текст. Снимки на диске
и JSON HTTP-запросов по-прежнему UTF-8; схема и значения записей не меняются.

## Первый локальный разбор

```bash
lookatshow-bitrix-read validate --input ./snapshot.json
lookatshow-bitrix-read audit --input ./snapshot.json --as-of 2026-10-10T10:00:00+03:00
```

У снимка `schema_version: 1`, источник `synthetic` или `bitrix24_webhook`, время
`capture_started_at` и `captured_at` с часовым поясом, флаг `deals_complete`, список `deals` и запись
`activity_reads` для каждой сделки. Минимальный учебный пример:

```json
{
  "schema_version": 1,
  "source": "synthetic",
  "capture_started_at": "2026-10-10T10:00:00+03:00",
  "captured_at": "2026-10-10T10:00:00+03:00",
  "deals_complete": true,
  "deals": [{"id": 5111, "categoryId": 0, "assignedById": 29, "stageSemanticId": "P"}],
  "activity_reads": [{"deal_id": 5111, "complete": true, "items": []}]
}
```

У дел остаются только поля `ID`, `COMPLETED`, `DEADLINE`. Одно общее дело может
быть связано с двумя сделками — оно должно остаться у обеих. Невалидную дату,
противоречащие записи или неверные поля нельзя тихо превращать в пустой список.
Локальный снимок может содержать завершённые дела: отчёт исключает их из
незавершённых. Reader отклоняет завершённые записи, неожиданно пришедшие по
фильтру `COMPLETED=N`. `capture_started_at` и `captured_at` задают начало и конец
сбора; отчёт показывает это окно в `capture_window` и отдельно область
видимости. Чтение нескольких страниц — последовательные запросы, не одна
замороженная транзакция.

## Как прочитать свой портал

Создайте входящий webhook с доступом к CRM по
[официальной инструкции Битрикс24](https://apidocs.bitrix24.com/local-integrations/local-webhooks.html).
Лучше использовать отдельного пользователя с правом чтения нужной области.
Сам CRM-webhook у провайдера может иметь более широкие права: режим read-only
обеспечивается **списком из двух разрешённых методов нашего модуля**, а не просто
фактом существования webhook.

`B24_WEBHOOK_URL` — секрет. Не вставляйте его значение в промпт, issue, скриншот
или командную строку. В интерактивном POSIX-терминале можно ввести его без эха:

```bash
read -r -s B24_WEBHOOK_URL
export B24_WEBHOOK_URL
lookatshow-bitrix-read doctor
lookatshow-bitrix-read capture --out ./private-crm-snapshot.json --max-deal-pages 2 --max-activity-pages 2
unset B24_WEBHOOK_URL
```

После этого запустите `audit --input ./private-crm-snapshot.json --as-of RFC3339`
с настоящим временем разбора и часовым поясом — не раньше `captured_at` в снимке.
Не переносите фиксированную дату учебного примера на новый capture. Если срок
равен `null` или пустой строке, это `unknown_deadline`; только валидный специальный
признак провайдера подтверждает `undated`. Неправильная дата даёт ошибку проверки,
а не догадку.

Необязательное приветствие локальное и к CRM не обращается:

```bash
lookatshow-bitrix-read onboard --state-dir ./local-onboarding
```

Текущий reader поддерживает только облачные HTTPS-порталы под `.bitrix24.ru`
и `.bitrix24.com`. Нет OAuth, коробочной версии, своего домена или хранения
доступов. Перенаправления и произвольные методы API отклоняются. Каждый поток
начинается с нуля и продолжает чтение по `next` из ответа провайдера. Лимит
страниц дел действует отдельно для каждой сделки. Если лимит достигнут,
фиксируется неполная выборка, а не ложное отсутствие дел.

Capture создаёт **только новый файл**, без перезаписи, с правами `0600` на POSIX.
Webhook в файл не попадает. Имена, телефоны, email, названия и суммы сделок
не собираются, но внутренние ID позволяют связать записи с вашей CRM.
**Это не обезличивание.** Не загружайте снимок на GitHub, в публичный чат или
посторонний ИИ-сервис. Перед передачей агенту проверьте свои разрешения на
работу с такими данными.

## Что именно читается и где пруфы

Всего два read-метода через JSON POST:

- [`crm.item.list`](https://apidocs.bitrix24.com/api-reference/crm/universal/crm-item-list.html):
  `entityTypeId=2`, `stageSemanticId=P`, минимальные поля сделки в camelCase.
- [`crm.activity.list`](https://apidocs.bitrix24.com/api-reference/crm/timeline/activities/activity-base/crm-activity-list.html):
  `COMPLETED=N` и `BINDINGS` конкретной сделки, минимальные поля дела в UPPER_CASE.

Поле `opened` говорит о видимости другим сотрудникам, а не о состоянии «сделка
в работе». Смотрите [поля CRM-объектов](https://apidocs.bitrix24.com/api-reference/crm/universal/object-fields.html)
и [официальный пример срока 9999-12-31](https://apidocs.bitrix24.com/tutorials/crm/how-to-get-lists/get-activity-list-by-deals.html).
Устаревший `crm.deal.list` не используется. Исследование документации — не
live-проверка: HTTP-тесты работают с подставными ответами, настоящий портал
на этом этапе не читался.
